# Coding Agent Instructions

This file is the primary instruction file for Gemini CLI or another coding agent working in this repository.

## Read Order

Before changing code, read these files in order:

1. `PLAN.md`
2. `ARCHITECTURE.md`
3. `DIRECTORY_STRUCTURE.md`
4. `DATABASE.md`
5. `API.md`
6. `ROUTES.md`
7. `UI_RULES.md`
8. `WORKFLOWS.md`
9. `SECURITY.md`
10. `SEED.md`
11. `TESTING.md`
12. `DEFINITION_OF_DONE.md`

If an implementation decision conflicts with these documents, the more specific document wins. Do not silently ignore a rule; update documentation with the same change when requirements change.

## Agent Behavior

- Implement in vertical slices, not disconnected UI-first batches.
- Inspect existing code before creating a competing abstraction.
- Reuse current project patterns.
- Keep changes scoped to the current milestone.
- Never fabricate an API response or database result to make UI appear complete.
- Never use hard-coded arrays as a substitute for unfinished database work.
- Never place database queries directly in React client components.
- Never place table declarations outside `db/schema/`.
- Never put all tables in `db/schema.ts`.
- Never place all queries in one `queries.ts`.
- Never trust client-computed invoice totals, permission flags, ownership, or status transitions.
- Every destructive/financial/clinical mutation must be auditable.
- Do not introduce a dependency merely to avoid writing a small, clear function.
- Do not duplicate shadcn/ui primitives.
- Use `bun` consistently.

## Required Verification After Every Milestone

Run:

```bash
bun typecheck
bun lint
bun test
bun build
```

When database schema changes:

```bash
bun db:generate
bun  db:migrate
```

On a clean development/test database also verify:

```bash
bun db:seed
```

Do not mark the milestone complete when any command fails.

## Implementation Decision Rules

- Server Components by default.
- Client Components only for stateful interactions, browser APIs, event handlers, and client-only libraries.
- Prefer explicit service functions for workflows spanning multiple tables/domains.
- Query modules perform database access; service modules enforce business workflows.
- Route handlers are transport boundaries, not business-logic containers.
- Keep schemas and DTO validation separate from UI form rendering.
- Use database constraints in addition to application validation.
- Use transactions for cross-table consistency.
- Use indexes for frequent foreign-key lookup, status/date filtering, and unique business identifiers.

## No Static Business Data Rule

Forbidden in page/component/API code:

```ts
const patients = [/* demo patients */]
const doctors = [/* demo doctors */]
const appointments = [/* demo appointments */]
```

Allowed static values are presentation/configuration constants only, for example:

```ts
const PAGE_SIZE_OPTIONS = [10, 20, 50]
```

Enums/status options should originate from shared domain constants/types tied to schema definitions when practical.

All demo hospital records must be generated by `db/seed.ts`.

## Error Handling

- Use typed domain errors where useful.
- Convert known errors into stable API error codes.
- Do not expose stack traces, SQL, internal IDs that should remain hidden, or secrets to clients.
- Log server errors with request context but never log passwords, session tokens, or sensitive clinical content unnecessarily.

## Git Hygiene

- Keep commits cohesive.
- Never commit `.env` or production secrets.
- Include migrations when schema changes.
- Do not edit generated migrations after they have been applied to a shared environment; create a new migration.
